# 第一期演示流程

这份流程用于本人在企微客户端演示。自动验收证据见 [聊天链路验收](phase1-chat-acceptance.md)，不要将脚本回调的录屏描述为手动操作录屏。

## 准备

确认 Vey、HTTPS 网关和企微可信 IP 配置正常。应用可见范围只包含本人，演示前遮住企业 ID、成员联系方式、密钥和服务器登录信息。

管理员在服务器创建已登记的临时测试服务：

```bash
cd /opt/vey
docker compose -f tests/fixtures/acceptance.compose.yaml up -d
```

不要拿数据库、Redis 或 Agent 自身做启停示范。日志分页演示需要预先生成足量合成日志，验收脚本会生成测试数据；运行该脚本也会执行测试容器启停、清理会话及发送回复，不能误当成只生成日志的命令。

## 建议演示顺序

| 发给 Vey 的消息 | 观察点 | 可以解释的工程设计 |
| --- | --- | --- |
| `服务器概况` | 中文摘要、采样时间、内存单位、运行时长 | 确定性查询无需模型；展示数据来源范围，不把容器指标冒充宿主机 |
| `日志 测试服务` | 最近日志、脱敏、分段编号 | 日志同时受行数与字符上限约束，分段进度持久化 |
| `下一页` | 更早的日志，保持快照顺序 | 游标绑定会话与目标容器，容器变更或会话失效后拒绝旧游标 |
| `请只读排查测试服务是否正常，引用证据说明结论` | 容器状态、日志、业务健康及 E1 等证据 | 模型选择固定只读工具；最多 5 次调用、60 秒；缺少证据时说明不确定性 |
| `重启 测试服务` | 展示目标、容器和两分钟确认码 | 模型或用户的操作请求只生成待确认记录，没有立即执行 Docker |
| `确认 <刚收到的8位确认码>` | 执行结果及业务健康检查 | 工具层复核身份、保护规则、容器快照；一次性消费确认 |
| 再次发送同一确认 | 返回原操作结果，不再次重启 | 去重与执行记录；不承诺跨 Docker／数据库原子事务 |
| `停止 数据库` | 直接拒绝 | 保护规则在执行器内检查，模型无法通过提示覆盖 |
| `清空上下文` | 提示上下文清空、审计保留 | 会话数据与审计生命周期分离 |

为减少手机端刷屏，录制时可分成“查询／排查”和“确认／安全”两段。操作结果仍有部分结构化 JSON；不要把尚未完成的管理后台或 Jev 接入展示成现有功能。

## 演示结束

保存需要的任务编号供审计查询，清空测试会话，然后仅清理测试项目：

```bash
docker compose -f tests/fixtures/acceptance.compose.yaml down
```

## 面试中说明的边界

- PostgreSQL 保存任务、会话、投递进度、确认事实与摘要审计；执行器角色不能修改核心 schema，核心角色不能消费执行器确认。
- 核心不持有 Docker socket；执行器仍具有接近宿主机 root 的 Docker 权限，因此进程分离和白名单不是对执行器被攻破的绝对防护。
- 对结果未知的操作保留证据、拒绝自动重放；管理员核对后才解除后续操作锁定。
- 企微接口接受消息与本地记录投递进度不能原子提交，可能出现同一分段的重复窗口。
- 第一期的实际测试、尚未覆盖的条件和后续待办以验收记录为准。第二期计划建立评测集，衡量诊断正确性、危险操作误判、工具选择、耗时和成本，再做模型／Jev 对比。
